# 電子發票研究筆記（後端工程師請先讀這份）

> 對象：接手金吉利 ERP 電子發票功能的後端工程師。
> 目的：說明需求、目前查到的法規與綠界做法、示範版已做到哪裡、還有哪些**必須再查證**的地方。
> 讀完這份再看 `docs/DB_preparation_list.md`（資料庫建議）與程式碼。
> 研究日期：2026-10-29。法規與加值中心規格會變動，**上線前每一條都要對照財政部最新公告再確認一次**。標示「待查」的項目，代表我沒有找到可靠的官方來源。

## 1. 需求（客戶原話整理）

1. 金吉利原本用**綠界科技（ECPay）**開電子發票，客戶滿意；因合約因素無法續用，希望由我們的系統接手電子發票，並自動處理稅務相關流程。
2. **以「單趟」開立為主**：每一趟送貨開一張發票，印出交給客戶。
   系統內的「月結對帳單」是金吉利額外提供給客戶的對帳資料，**不是發票**，兩者不衝突。
3. 客戶（金吉利的客戶）報價方式不一：**有的含稅、有的未稅、有的混合**（同一客戶部分品項含稅、部分未稅），要能讓金吉利自行調整。
4. 最終要印給客戶的單據長這樣（客戶提供的綠界單據照片，數字如下）：

```
交易明細
買受人統編 ********
買受人名稱 ****************
2026-05-05 00:00:00
--------------------------------
品名            單價*數量        金額
03F05001 酥炸杏鮑菇-金吉利
      361.9047619*9
                 3,257.1428571 TX
12F01008 脆薯-3/8-(G)
      1,209.5238095*1
                 1,209.5238095 TX
--------------------------------
合計 2 項
銷售額(應稅) $4,467
稅額 $223
總計 $4,690
```

（照片中有真實買受人的統編與名稱，這裡刻意遮掉；示範資料不要使用真實客戶資料。）

## 2. 從這張單據反推綠界的算法（已驗證）

| 欄位 | 單據數字 | 計算 |
|---|---|---|
| 杏鮑菇單價 | 361.9047619 | 含稅 380 ÷ 1.05，取到小數 7 位 |
| 杏鮑菇金額 | 3,257.1428571 | 含稅 3,420（380 × 9）÷ 1.05 |
| 脆薯 | 1,209.5238095 | 含稅 1,270 ÷ 1.05 |
| 總計 | 4,690 | 3,420 + 1,270（**含稅金額直接相加**） |
| 稅額 | 223 | 4,690 ÷ 1.05 × 0.05 = 223.33 → 四捨五入 |
| 銷售額 | 4,467 | 4,690 − 223 |

結論：**含稅報價時，以「含稅總額」為準，稅額由總額倒推，銷售額 = 總額 − 稅額**；品項的未稅單價／金額保留到小數 7 位。這與綠界文件公布的「一般發票稅額 = 發票金額 ÷ 1.05 × 0.05，四捨五入至整數」一致。

> 為什麼重要：如果反過來「先把含稅單價換算成整數未稅價再加稅」（例如 380 → 362），9 包就會變成 3,421 而不是 3,420，客戶對帳會差 1 元。示範版原本就是這樣做，這次已改正。

## 3. 法規與規格重點

> 來源清單見第 12 節。凡是出自業者文章而非官方文件的，已標註。

### 3.1 規格版本
- 一律使用 **MIG 4.0**（財政部「電子發票資料交換標準訊息建置指引」）。舊版 MIG 3.2.1／3.1.2 自 **2026/1/1 停用**（業者文章與 Sovos 說明；財政部平台另有 MIG 4.1 文件，**待查**兩者差異）。
- MIG 4.0 把訊息合併為：**F0401** 開立、**F0501** 作廢、**F0701** 註銷、**G0401** 折讓、**G0501** 作廢折讓（另有 E0402 空白未使用字軌等，**待查**完整清單）。
- 每個 XML 檔只能含一張發票；紙本證明聯顯示的內容必須和上傳內容一致（財政部 Turnkey 自行檢測文件）。

### 3.2 數字欄位
- **單價：整數 10 位、小數 7 位；金額：整數 12 位、小數 7 位**（綠界 MIG 4.0 文件；財政部指引亦寫明最多小數 7 位）。
- 綠界開立 API：品項單價**固定填未稅價**；查詢 API 回傳的單價卻是**含稅**——兩者方向相反，串接時要注意。
- 綠界的檢核（可視為合理的內部檢核標準）：
  - |稅額 − round(銷售額 × 5%)| ≤ 2
  - 品項金額與「數量 × 單價」四捨五入後的差距 ≤ 1

### 3.3 稅額與證明聯
- 買受人為營業人時，**銷售額與稅額必須分別列示**（營業稅法第 32 條）；應稅、零稅率、免稅銷售額也要分別列示。品項課稅別印 **TX（應稅）／TZ（零稅率）**（免稅代號 **待查**）。
- 冷凍食品**應該都是應稅**，但請會計確認有沒有免稅或零稅率品項。

### 3.4 上傳期限與罰則（114 年／2025 新制）
- 開立、作廢、折讓都要上傳。**B2B（買方有統編）：開立翌日起 7 日內；B2C：2 日內**。期限末日遇假日**不順延**。
- 因不可抗力無法如期上傳：事由消滅翌日起 3 日內向稽徵機關申請補正。
- **折讓單一律由賣方開立並上傳**（2025 年起）。
- 逾期或未據實上傳：**營業稅法第 48 條之 2，處 1,500 元以上、15,000 元以下罰鍰**。
- 有業者文章提到折讓新制輔導期到 2025/6/30，現已正式適用（單一來源，**待查**）。

### 3.5 存證 vs 交換
- **存證**：賣方開立後列印或寄送給買方，再上傳財政部；**不需要買方確認**。
- **交換**：不印紙本，透過平台傳給買方，**買方要上線確認**。
- 金吉利是印出來交給客戶 → **存證模式**。

### 3.6 證明聯列印
- 格式一：熱感紙寬 **5.7 公分（±3%）**；格式二：寬 21 公分（限營業人與營業人交易）。
- **買受人為營業人（或要求記載統編）：交易明細接在二維條碼下方列印，不裁切**；買受人為消費者：明細自二維條碼下方裁切（雙方同意可免附）。客戶照片就是前者。
- 統編欄位印「賣方」／「買方」（或「賣方統編」／「買方統編」），兩者印法要一致。
- 一維條碼與兩個 QR Code 的內容規格見財政部「電子發票證明聯一維及二維條碼規格說明」；**QR Code 需要財政部核發給營業人的加密金鑰（AES）**，要向客戶取得。

### 3.7 字軌
- 營業人在財政部電子發票整合服務平台取號（選期別、類別、本數）。
- 年配：一次配到年底；期配：平台於**雙月 20 日**配下一期，依本期最後取用本數決定下期本數。
- 字軌可授權給加值中心使用。**從綠界切換時，要先在平台取消對綠界的授權並重新分配，避免號碼重複**（流程細節**待查**）。

### 3.8 統一編號檢查碼
- 自 2023/1/1 起由「可被 10 整除」改為「**可被 5 整除**」。示範版 `isValidTaxId` 已是新規則。

## 4. 計價方式（含稅／未稅／混合）—— 示範版的做法

程式：`src/lib/domain/taxcalc.ts`（測試：`src/lib/__tests__/taxcalc.test.ts` 用上面那張單據逐位驗證）。

| 單據報價方式 | 規則 |
|---|---|
| 含稅 | 總額 = Σ 品項含稅金額；稅額 = round(總額 × 5 / 105)；銷售額 = 總額 − 稅額 |
| 未稅 | 銷售額 = round(Σ 品項未稅金額)；稅額 = round(銷售額 × 5%)；總額 = 銷售額 + 稅額 |
| 混合 | 銷售額 = round(Σ 未稅品項 + Σ 含稅品項 ÷ 1.05)；稅額 = round(Σ 未稅品項 × 5% + Σ 含稅品項 × 5 / 105)；總額 = 銷售額 + 稅額 —— **這是我的建議，需會計師確認** |

- 四捨五入一律「四捨五入到整數元」（half-up）。
- 已驗證：整數元的含稅總額 1～20,000 元，倒推後 銷售額 + 稅額 一定等於原總額，不會差 1 元。
- **精度**：品項的 7 位小數用 **BigInt（單位 10⁻⁷ 元）** 計算，存成字串（例如 `"361.9047619"`）；整張單據的金額用整數「分」。**全程不用浮點數**。資料庫請用 `NUMERIC`，不要用 `float/double`。
- **尾差調整**：應收單據各品項的未稅分攤（分）加總必須剛好等於銷售額，差額放到金額最大的那一行（`allocateExTax`）。
- 報價方式的設定：
  - 客戶層級：`Customer.priceBasis`（含稅／未稅），在「客戶與應收 → 客戶資料 → 報價方式」切換，只影響之後的新訂單。
  - 品項層級：合約價（`CustomerPrice.quoted.taxIncluded`）可個別設含稅或未稅 → 同一客戶就會出現「混合」。
  - 訂單行記錄當時的報價方式與含稅單價（`OrderLine.priceBasis`、`unitPriceInclTaxCents`），之後改設定不影響已建立的訂單。
- 未稅等級價換含稅時（客戶設為含稅、但沒有合約價）：`round(未稅 × 1.05)` 到整數元。**這是示範假設**——實務上金吉利應該有自己的含稅價目表，請確認。
- 以「箱」報價的含稅價，換算每包時取到「分」（例如 2,289 ÷ 10 = 228.90）。若除不盡會有極小誤差，**待確認**是否改成以實際下單單位計價。

### 發票狀態（示範版沿用既有欄位）
`staged`（待預檢）→ `preflight_failed`（預檢未過，例如載具格式錯）／`ready`（**已開立・待上傳**，已有號碼）→ `accepted`（模擬已上傳）／`rejected` → 之後的 `voided`、`allowance`。
正式版建議把「開立狀態」與「上傳狀態」拆成兩個欄位，並加上作廢、折讓的獨立狀態，詳見資料庫建議。

## 6. 上傳通道：兩個選項

| | A. 另一家加值中心（光貿、藍新 ezPay、鯨躍、e首發票等） | B. 財政部 Turnkey 自行上傳 |
|---|---|---|
| 費用 | 月費約 99～199 元，或每張約 1.2～1.5 元（業者公告，**待確認**） | 軟體免費 |
| 上線時間 | 約 3～7 天 | 約 1～2 個月（工商憑證、上線前自行檢測、常開主機） |
| 合約 | 仍需與加值中心簽約 | 不需廠商合約 |
| B2C 載具／捐贈／中獎 | 加值中心處理 | 自己處理（複雜度高，**實作方式待查**） |
| 我們要做 | 呼叫對方 API | 產生 MIG 4.0 XML 放入 Turnkey 目錄、讀回處理結果 |

建議：**開票引擎、字軌、列印、期限監控由我們自己做**（兩個選項都需要）；上傳做成可替換的轉接器（`TurnkeyAdapter`／`VacAdapter`）。客戶最在意「不要再綁合約」→ B；在意快速上線或 B2C 載具客戶多 → A。**由客戶決定**。

## 7. 建議的正式版流程

1. 送達 → 建立應收 → 依報價方式計算 → 建立發票草稿。
2. 預檢（統編、載具、金額、稅額、品項）。
3. 取號：從當期有效號段取下一號，**在資料庫交易中鎖定號段**，確保不重複、不跳號。
4. 開立：寫入發票號碼、隨機碼、開立時間；**此後不可修改**。
5. 列印證明聯＋交易明細交給客戶。
6. 產生 F0401 → 上傳 → 讀回結果（成功／錯誤）→ 錯誤要能重送，並保留每次紀錄。
7. 期限監控：逾期前提醒（B2B 7 天／B2C 2 天）。
8. 更正只能透過：作廢（F0501）、註銷重開（F0701）、折讓（G0401）、作廢折讓（G0501）。
9. 期末：空白未使用字軌回報（次期開始 10 日內）；匯出銷項資料給會計申報 401。
10. 每一步寫入不可刪改的事件紀錄（示範版的 `ActionEvent` 可以沿用設計）。

## 8. 從綠界切換時要注意

- 目前授權給綠界的字軌：在財政部平台取消授權、重新分配給新通道，**切換當天的號碼不能重複也不能空缺**。
- 綠界上的舊發票：之後若要作廢或折讓，需要原發票資料 → 切換前**完整匯出**歷史發票（含明細）。
- 切換日前後的發票分屬不同通道，申報時要能合併。
- 綠界的「交易明細」版面是客戶習慣的格式，我們的列印版面已照它做。

## 9. 更多待查（More to look at）

請工程師開工前逐項查證、記錄結論與來源：

1. **MIG 4.1 vs 4.0**：財政部平台已有 MIG 4.1 文件與 Turnkey 使用說明書 Ver 4.1（2026/9），變更內容與生效日。
2. **F0401 欄位完整對照**：我們的 `InvoiceLine` / `TaxInvoice` 對應到 MIG 4.0／4.1 的哪些欄位（必填、長度、格式），特別是品名長度上限、單位、備註、課稅別、稅率、買受人資料。
3. **混合報價的稅額算法**：第 4 節的混合規則是否被會計師接受；也可能改成「同一張發票只能一種報價方式，混合就拆成兩張」。
4. **免稅與零稅率品項**：是否存在？課稅別代號（TX／TZ／TF？）與證明聯的列示方式。
5. **證明聯條碼與 QR Code**：「電子發票證明聯一維及二維條碼規格說明」最新版；QR 加密金鑰的申請與保管（放伺服器端祕密管理，不可放前端）。
6. **Turnkey 實際作業**：安裝環境、工商憑證、上線前自行檢測項目（Ver 4.7.1 之後是否改版）、回應檔（ProcessResult）的格式與重送機制。
7. **B2C 小店**：手機條碼、會員載具、捐贈碼、中獎通知與列印——自行用 Turnkey 時誰負責、怎麼做。
8. **作廢期限與跨期**：作廢在什麼期限前可做、跨申報期後只能折讓的確切規定（業者文章說法不一，請以財政部條文為準）。
9. **折讓單**：G0401 格式、賣方開立後是否需要買方確認、證明單列印格式。
10. **字軌授權轉移**：從綠界轉到新通道的平台操作步驟與時點。
11. **空白字軌回報**（E0402？）的格式與期限。
12. **證明聯「格式 25」**：B2B 證明聯上的格式代號規則（示範版先印「格式 25」，**待查**）。
13. **熱感印表機**：客戶實際機型，瀏覽器 `@page size: 57mm` 列印是否準確；必要時改用印表機 SDK 或 ESC/POS。
14. **開立時間**：照片上的開立時間是 `00:00:00`（只有日期）。正式版要記錄實際開立時間還是交易日期？與上傳期限的起算日有關。
15. **買方統編檢核**：除了檢查碼，是否要即時查詢營業登記（財政部或經濟部 API）。
